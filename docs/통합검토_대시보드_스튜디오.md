# 통합 방향 검토 자료 — 대시보드 ↔ 스튜디오

> 목적: 지금 두 개로 나뉜 화면(대시보드 / 스튜디오)을 어떻게 하나로 통합할지 결정. GPT 검토용 정리.
> 배경 한 줄: 사용자는 "대시보드에서 모든 게 이루어지는 줄 알았다"고 했고, "대시보드 UI/UX가 훨씬 낫다"고 평가함.

## 1. 현재 구조 (사실)

한 개의 Render 서비스(`medical-pipeline.onrender.com`) 안에 Flask 앱이 두 개 얹혀 있음.

| | **대시보드** (`/`) | **스튜디오** (`/studio`) |
|---|---|---|
| 코드 | `app.py` | `web/api.py` |
| 저장소 | SQLite(작업상태) + 파일(자료·산출물) | **PostgreSQL**(정규화·영속) |
| 로그인 | users.yaml 세션(별도) | PG 유저 세션(별도) — **로그인 2개** |
| UI/UX | **높음**(토스풍, Pretendard, 카드) | 낮음(기능 위주, 디자인 미흡) |
| 배포 상태 | 라이브 | 라이브(`/studio` 마운트) |

마운트는 `app.py`에서 `DispatcherMiddleware`로 `/studio`에 스튜디오를 얹은 형태. 두 앱은 세션·데이터가 서로 분리됨.

## 2. 왜 이렇게 됐나 (의도 아님, 과도기)

- 대시보드가 **먼저** 만들어진 MVP(자료 업로드 → 대본 생성 → 리포트).
- 스튜디오는 **나중에** P0 재설계(대본→버전(immutable)→블록→문장→claim→근거→검수·승인)로 PostgreSQL 위에 새로 구축.
- 라이브에 올릴 때 "기존 대시보드 안 건드리고" `/studio`로 안전하게 얹음 → **결과적으로 둘로 분리**. 계획된 2-제품이 아니라 순서 때문에 생긴 과도기 상태.

## 3. 핵심 문제

1. **연결 안 됨**: 대시보드에서 만든 대본이 스튜디오 DB로 자동 안 넘어감. 스튜디오엔 수동 적재한 이명편 1개뿐.
2. **로그인 2개 / 저장소 2곳**(SQLite vs PostgreSQL).
3. **사용자 혼란**: "다 대시보드에서 되는 줄 알았다."
4. **UI/UX 격차**: 대시보드는 완성도 높고, 스튜디오는 부실.
5. **영속성**: 대시보드의 업로드·산출물은 Render 무료 티어에서 **ephemeral**(재시작·재배포 시 소실). 스튜디오 PG는 영속.

## 4. 기능 매핑 (누가 뭘 갖고 있나)

| 기능 | 대시보드 | 스튜디오 |
|---|---|---|
| 자료 업로드 | ✅ | ❌ |
| 대본 AI 생성(run.py) | ✅ | ❌ |
| 대본 편집(문장 단위) | ❌(정적 리포트) | ✅ |
| 버전/이력/diff | ❌ | ✅(immutable 버전) |
| 근거검증 | ✅(리포트 1차 의견) | ✅(LLM per-claim, 검수/반려, 승인 게이트) |
| 장면 이미지 | 프롬프트/스톡링크만 | ✅(실제 생성·재생성·라이트박스, DB저장) |
| 멀티테넌트 격리 | 약함(폴더 분리) | 강함(PostgreSQL RLS) |
| 영속성 | 약함(SQLite/ephemeral) | 강함(PostgreSQL) |
| UI/UX 완성도 | **높음** | 낮음 |

요약: **"만드는 힘"은 대시보드**(업로드·생성·예쁜 UI), **"다루는 힘"은 스튜디오**(편집·버전·근거·이미지·승인·영속). 지금은 둘이 끊겨 있음.

## 5. 통합 옵션

**A. 대시보드=허브 + 스튜디오로 링크스루**
대시보드에서 생성 → 자동으로 스튜디오 PG 적재 → 대시보드에 "편집·근거·이미지" 버튼 → 누르면 스튜디오 화면.
- 장점: PG 기능 유지, 대시보드 UI 유지, 작업량 중간.
- 단점: 넘어가면 **스튜디오의 부실한 UI**를 만남(UI 이원화 그대로).

**B. 프론트=대시보드 하나로 통일 + 백엔드=스튜디오(PostgreSQL) 재사용** ← 추천
편집·근거·이미지·승인 화면을 **대시보드 디자인 언어로** 다시 그리되, 데이터는 스튜디오 PostgreSQL/RLS를 그대로 사용(재구현 아님, API만 호출).
- 장점: **한 화면(예쁜 대시보드)에서 전부**, 영속·버전·격리 유지, 로그인 1개로 통일.
- 단점: 프론트 재작업(디자인 이식) 필요. 다만 백엔드 로직(버전·근거·승인·이미지)은 이미 있으니 재사용.

**C. 스튜디오=홈(대시보드 흡수)**
- 사용자가 스튜디오 UI를 선호하지 않음 → 그대로는 제외. (스튜디오에 대시보드 CSS를 이식하면 B와 수렴.)

## 6. UI/UX 관찰 (중요 입력)

- 대시보드 디자인이 명백히 우위(토스풍, Pretendard, 흰 카드, #3182F6). 스튜디오는 P0 백엔드 검증용 기능 UI라 디자인 미흡.
- 따라서 **최종 화면의 기준 디자인 = 대시보드**. 어느 옵션이든 사용자 눈에 닿는 화면은 대시보드 톤으로 통일하는 게 맞음. → 이 관찰이 **옵션 B**를 지지.

## 7. 리스크 / 선결 과제

1. **대본 생성 결과의 PG 적재**: 지금 run.py는 파일/SQLite로 씀 → 스튜디오 PG(대본→버전→블록→claim)로 적재하는 파이프라인 필요(이명편은 수동으로 함).
2. **업로드/산출물 영속성**: Render 무료는 파일 ephemeral. 진짜 영속하려면 PG bytea / 오브젝트 스토리지 / 유료 디스크 중 택1.
3. **로그인 통합**: 현재 2개 → 1개(어느 인증을 표준으로).
4. **기존 대시보드 흐름 보존**: 통합 중 기존 사용 깨지지 않게.
5. **작업량**: 옵션 B는 프론트 재작업이 가장 큼(그러나 UX 최선).

## 8. GPT에게 물을 결정 질문

1. **옵션 A vs B**: 링크스루(빠름, UI 이원화 유지) vs 대시보드 UI로 프론트 통일(느림, UX 최선). 어디로?
2. 대본 생성 결과를 스튜디오 PG에 **자동 적재**하는 파이프라인 설계(생성 시점에 대본→버전→블록→claim 트랜잭션).
3. 업로드/이미지 **영속성** 해결책: PG bytea vs 오브젝트 스토리지(예: Cloudflare R2/S3) vs Render 유료 디스크?
4. 로그인/세션 **단일화** 방식.
5. 통합을 **점진적**으로(대시보드에 스튜디오 링크부터 → 이후 프론트 흡수) 갈지, 한 번에 갈지.

## 9. 정리 의견(작성자)

- 사용자 선호(대시보드 중심 + 대시보드 UI 우위)를 반영하면 **옵션 B**(백엔드=스튜디오 PostgreSQL 유지, 프론트=대시보드 디자인으로 통일)가 방향으로 맞다고 봄.
- 단, **점진적**으로: (1단계) 대시보드에서 대본 생성 시 스튜디오 PG에도 적재 + 대시보드에 "편집/근거/이미지(스튜디오)" 연결 → (2단계) 그 화면들을 대시보드 디자인으로 흡수 → (3단계) 로그인·업로드 영속 통일.
- 이렇게 하면 지금 라이브를 안 깨고 단계적으로 하나로 수렴.

## 10. 확정판 (GPT 검토 반영, 2026-08-02)

**결정: 최종 아키텍처 = 옵션 B, 마이그레이션 전략 = A → B.**
PostgreSQL을 단일 원본(SoT)으로 만들고, 대시보드 UI가 PG 기반 편집·근거·이미지·승인 기능을 직접 쓰도록 점진 통합. `/studio`는 임시 운영화면(최종 폐기/관리자용).

### 원칙 (이중 유지보수 방지)
- 최종 사용자 화면은 **대시보드 디자인 하나**. `/studio`에서 새 기능 개발 금지.
- 신규 기능은 **공통 서비스/API 계층**에 구현(UI는 대시보드가 호출).
- SQLite는 조회 호환용으로만, **신규 쓰기는 PostgreSQL만**.
- 파일(업로드·이미지·산출물)은 **오브젝트 스토리지(R2/S3) + PG 메타데이터**. bytea는 작은 스냅샷만(현재 scene_images bytea는 MVP, P1에서 이전).
- 로그인 1개(PG 사용자/병원 표준, users.yaml 제거). 세션 user_id·hospital_id·role → RLS.

### 생성 파이프라인 (LLM을 트랜잭션 밖으로)
1차 tx: `generation_job` 생성 → 원본 AI결과 저장 → script/version/block/sentence 적재 → COMMIT.
2차(async): claim 추출(LLM) → claim/근거후보 적재 → 검증상태 → COMMIT.
`generation_job` 필드: id, status(pending/generating/parsed/verifying/completed/failed), **idempotency_key**(중복 생성 방지), raw_output, error_message, retry_count, created_by, source_version, prompt_version.

### 문서에서 빠졌던 리스크 (추가)
- **P0 병원 내부 역할 권한**: RLS는 병원 간 격리만. 병원 안 원장/마케터/검수자/관리자별 가능 행동(생성·수정·반려·승인·이미지재생성·초대) 분리 필요.
- **P0 실패/재시도 상태**: 생성·claim·이미지 실패 시 "멈춤/실패/재시도" 구분 표시.
- **P0 기존 데이터 마이그레이션**: 초기엔 "기존 SQLite/파일 = 읽기전용 보관 + 신규는 PG"가 가장 안전.
- **P1**: PG 백업·복구 테스트, 스토리지 삭제정책·cascade, 실패로그·관리자화면, 감사로그 조회, 중복생성 방지, 프롬프트·자료 버전 기록(재현·책임소재).

### 구현 순서 (데이터·인증부터, UI는 나중)
- **1단계 — 연결(기존 안 깨기)**: PG를 신규 기준 저장소로; 대시보드 로그인 → PG 사용자 연결; 생성결과 script/version/block/sentence 적재(idempotency); 생성 후 "대본 편집" 버튼 → 임시 `/studio`; 실패/재시도 상태.
- **2단계 — 흡수(사용 많은 순)**: 대본편집 → 근거검증 → 승인 → 이미지 → 버전 diff 를 대시보드 디자인으로 이전.
- **3단계 — 완전 통합**: users.yaml 제거, SQLite 신규쓰기 중단, 기존 데이터 읽기전용/이전, 업로드·이미지 R2/S3, `/studio` 관리자용/제거, 옛 URL 리다이렉트.

**핵심 교훈: UI부터 합치면 겉만 하나(저장소·로그인·상태는 둘). 데이터·인증부터 합치면 /studio가 남아도 시스템은 사실상 하나.**
