# P0 설계 보고 — 대본 편집·버전·리뷰·근거검증 구조 (구현 전 분석)

작업 순서 1~6번(블록구조/버전 → 편집·diff·재검사 → 외부 댓글링크 → Correction Memory → Style Rule → Source Grounding)의 **현재 코드 영향 범위와 데이터 모델**을 분석한 보고서. 실제 수정은 이 보고 승인 후 착수.

---

## 0. 현 상태 요약 (근거: 실제 코드)

| 영역 | 현재 | 한계 |
|---|---|---|
| 대본 저장 | `data/<h>/out/<topic>_package.json` **단일 JSON 블롭** | 버전·수정이력·승인상태 없음 |
| 스크립트 블록 | `script[]`, 필드 = `{tc, block, scene, say, tags}` | **block_id·type·status·version·source 없음** |
| 근거 검증 | `evidence/check.py` — `papers[]` **요약 단위** 대조 | **문장(say)별 claim 매핑 아님** |
| 의료광고 검수 | `compliance/rules.py` `check()/report()` — say+scene 정규식 | 문장별 근거·수정 후 재검사 훅 없음 |
| 원장 검수 | 대시보드 O/X = **localStorage** | 서버 저장·회수·승인상태 없음 |
| DB | `data/jobs.db` — 테이블 **`jobs` 1개**(hospital PK, topic, status, ok, log, updated) | 대본·버전·댓글·수정·claim 테이블 없음 |
| 웹 라우트 | `/`, `/new`, `/h/<h>`, `/upload`, `/run`, `/status`, `/view/<fn>`, `/login`, `/logout` | 편집·댓글·버전·리뷰링크 라우트 없음 |
| 권한 | `users.yaml` 단일 계정(역할 구분 없음) | editor/reviewer/approver 구분 없음 |
| 생성 프롬프트 | `director.md` — "의학 주장 문장은 논문 1편 매핑, 없으면 삭제/톤다운" **지시는 존재** | 구조적으로 **강제·캡처 안 됨**(출력에 source 없음) |

**핵심 결론**: 근거 결착의 *의도*는 프롬프트에 있으나, 출력 구조가 이를 담지 못해 검증·차단이 불가능하다. → 데이터 모델을 **블록·claim·버전 중심**으로 재설계하는 것이 1~6 전체의 토대.

## 1. 현재 대본 저장 구조

- 생성: `run.py cmd_episode` → `llm/runner.py generate(director.md, KB)` → 프롬프트-지시 JSON 파싱 → `<topic>_package.json` 저장.
- 사이드카: `.evidence.json`(근거 1차검수), `.assets.json`(시각자료). `render.py`가 이들을 읽어 `_package.html` 생성.
- 대본 본문 = `script[]` 배열, 블록당 `{tc, block, scene, say, tags}`. **say = 긴 문자열 한 덩어리**(문장 분리·식별자 없음).
- 결과물 `out/`만 git 추적, `raw/corpus/kb`·사이드카·zip은 gitignore.

**영향**: 스펙이 요구하는 `block_id/type/status/version/source_claim_ids`와 문장별 claim은 현 구조에 **필드가 아예 없음** → 스키마 확장 + 마이그레이션 필요.

## 2. 버전 관리를 추가할 파일 / 데이터 모델

**설계 원칙**: 생성 결과 JSON은 유지하되, **SQLite를 "버전·수정·댓글·claim의 시스템 오브 레코드"**로 승격. `jobs.db` → `data/app.db`(또는 병원별 `data/<h>/pipeline.db`)로 확장. 대본 본문은 버전 행에 JSON으로 저장(스냅샷) + 블록/claim은 정규화 테이블로 인덱싱.

**추가/수정 파일**:
- `store/db.py` (신규) — 스키마·마이그레이션·CRUD. (기존 `app.py`의 `_db/job_*`를 여기로 이관·확장)
- `run.py cmd_episode` — 생성 직후 **블록 ID 부여 + v1 버전 행 생성 + claim 추출** 저장.
- `render/render.py` — 블록 `data-block-id`, 버전 표시, 문장별 근거 패널 렌더.
- `app.py` — 편집·버전·댓글·리뷰링크 라우트 추가.
- `llm/prompts/director.md` — 출력에 블록 `type`, 문장별 `claims[]`(text·source_ids·support_level·medical_risk) 포함하도록 스키마 강화.

**제안 스키마(요지)**:
```
scripts(id, hospital_id, topic, created_at, approved_version_id NULL)
script_versions(id, script_id, version_no, content_json, status,           -- draft|review_requested|approved
                created_by, source, created_at, parent_version_id)          -- source: ai|editor
blocks(id, version_id, block_id, idx, type, tc_start, tc_end, text,         -- type: intro|explanation|evidence|transition|example|cta
       status)                                                              -- draft|review_requested|approved
claims(id, version_id, block_id, claim_id, text, support_level,            -- direct|partial|inferred|unsupported
       medical_risk, source_ids_json, source_quote)                         -- low|medium|high
sources(id, hospital_id, kind, ref, title)                                  -- kind: paper|kb|survey ...
edits(id, hospital_id, version_id, block_id, before_text, after_text,
      category, reason, created_by, created_at, approved_for_learning, scope)
comments(id, hospital_id, script_version_id, block_id NULL, reviewer_name,
         comment, status, created_at)                                       -- open|accepted|rejected|resolved|needs_discussion
review_links(token PK, hospital_id, version_id, role, expires_at, revoked,
             created_by, created_at)
style_rules(id, hospital_id NULL, scope, category, rule_text, example_before,
            example_after, approved, created_at)                            -- scope: hospital|doctor|topic|global
users(username, pw_hash, role)                                              -- editor|reviewer|approver (기존 users.yaml 이관)
```
블록·claim은 **버전마다 스냅샷**(불변). 편집 = 새 버전 생성이 원칙(원본 보존 원칙 6 충족).

## 3. 외부 리뷰 링크 권한 구조 (P0-3)

- **역할 3종**을 `users`에 도입: `editor`(직접수정), `reviewer`(댓글만), `approver`(최종승인). 기존 admin → editor+approver로 마이그레이션.
- **외부 리뷰 링크** = 로그인 없이 접근하는 **토큰 게이트 읽기전용** 경로. `review_links` 행으로 관리:
  - `token` = `secrets.token_urlsafe(32)` (예측 불가), `expires_at`(만료), `revoked`(관리자 폐기), `version_id`(특정 버전만), `role=reviewer`.
- 신규 라우트(예): `GET /r/<token>`(대본 버전 읽기+댓글 폼), `POST /r/<token>/comment`(블록/전체 댓글). **직접 편집 라우트는 토큰 접근에서 차단.**
- **노출 최소화**: 리뷰 화면은 해당 **버전의 블록 텍스트 + 댓글**만. `raw/corpus/kb` 원본, 다른 병원·다른 대본은 절대 미노출(모든 쿼리를 `token→version_id→hospital_id`로 스코프).

---

## 4. 수정 이벤트 데이터 모델 (P0-4 Correction Memory)

- 사용자가 문장 수정 → `edits` 행 저장: `{before_text, after_text, category, reason, created_by, scope, approved_for_learning=false, created_at}`.
- **흐름**: 수정 → before/after diff → LLM이 `category`(tone/awkwardness/factual/source_grounding/transition/disclaimer/intro/cta) **후보 분류** → **사람이 규칙 승인** → `style_rules`에 추가 → 다음 생성 시 `scope`(hospital/doctor/topic/global) 매칭 규칙·예시를 **검색해 director 프롬프트에 주입**.
- **명시적 안전장치**: 자동 전역화 금지. `approved_for_learning`이 true인 것만 규칙화, 오타·단발 수정은 규칙 승격 안 함. "모델 재학습" 아님 = 가중치 수정 없음, **프롬프트 주입(RAG)** 방식.

## 5. 기존 의료 검수와 연결 방법

- **두 게이트를 문장/claim 단위로 확장·직렬 연결**:
  1. `compliance/rules.py` (의료광고 금지어) — 이미 say+scene 검사. 편집 시 **변경 블록만 재검사** 훅 추가.
  2. `evidence/check.py` (논문 근거 대조) — 현재 `papers[]` 요약 단위 → **claim 단위로 확장**: 각 claim.text + source_ids를 KB/corpus 원문과 대조해 `support_level` 산정. `unsupported` → 승인 차단.
- **승인 규칙**: 블록/버전 `status=approved`는 (a) 금지어 PASS + (b) 모든 의료 claim이 `source_ids` 보유 & `support_level != unsupported` 일 때만 가능.
- **편집 시 자동 재실행**(스펙 P0-2): 수정 저장 → 의료 재검사 → 금지어 재검사 → source 연결 확인 → diff 저장 → **기존 승인 해제**(의료 문장 변경 시 재승인 강제). 이건 `app.py` 편집 라우트에서 `compliance.check` + `evidence` claim검증을 호출하는 파이프라인으로 구성.
- 대시보드/리뷰 화면: 문장별 **근거자료·근거문장·직접/해석·검토필요**를 `claims` 행에서 렌더(현 `render.py` 근거검수 섹션을 claim 단위로 확장).

## 6. source claim을 문장에 연결하는 방법 (P0-1)

- **생성 단계**: `director.md` 출력 스키마에 블록별 `claims[]` 추가 — 의학 문장마다 `{claim_id, text, source_ids, source_quote, support_level, medical_risk}`. (프롬프트엔 이미 "논문 1편 매핑" 지시가 있어 확장 부담이 낮음.)
- **검증 단계**: `evidence/check.py`를 재사용/확장 — claim.source_ids가 가리키는 KB/corpus 원문에서 `source_quote`·수치 실재 확인 → `support_level` 자동 재산정(모델 자기신고를 신뢰하지 않고 대조로 검증). 외부논문/미확인은 `partial|inferred|unsupported`로 강등.
- **차단 규칙**: `medical`(용어·수치·연구결과·기전) 문장이 `source_ids` 없이 최종 승인 불가. `unsupported`는 최종 대본에서 삭제/톤다운.
- **문장 식별**: say를 문장 단위로 분할(기존 렌더가 say 통짜라, 분할기 `nlp/segment.py`(경량 규칙) 필요). claim은 문장 span에 매핑.

---

## 7. 기존 데이터 마이그레이션 방법

- 대상: 현재 `data/<h>/out/*_package.json`(예: 이명 편).
- 절차(`store/migrate.py`):
  1. 각 package.json 읽어 `scripts` 1행 + `script_versions` v1(content=원본 JSON, status=`draft`, source=`ai`).
  2. `script[]` 각 원소에 `block_001..` 부여, `blocks` 행 생성, `type`은 휴리스틱 추정(block명 키워드: 콜드오픈→intro, 본론→explanation, 논문→evidence, CTA→cta …).
  3. claim은 **초기엔 비움**(기존 대본은 소급 claim 없음) → `evidence/check.py` 재실행으로 papers 근거를 claim 후보로 시드, `support_level=inferred`(사람 확인 대기)로 표시.
  4. 기존 `jobs` 테이블은 유지, `app.db`로 통합.
- **비파괴**: 원본 JSON은 삭제하지 않고 v1 content로 보존. 실패 시 롤백 가능하도록 마이그레이션은 트랜잭션 + 백업.

## 8. 예상되는 보안 위험

| 위험 | 대응 |
|---|---|
| 리뷰 토큰 추측/열거 | `secrets.token_urlsafe(32)`, 상수시간 비교, 실패 rate limit |
| IDOR(다른 병원·대본 접근) | 모든 쿼리를 `token/session → hospital_id → version_id`로 스코프, 교차 접근 거부 |
| 만료·폐기 우회 | 서버측 `expires_at`·`revoked` 매 요청 검사 |
| 댓글 XSS/HTML 주입 | 저장·렌더 양쪽 escape(현 `/view`는 자기 HTML 서빙이라 무해하나 **댓글은 사용자 입력**이라 필수) |
| 댓글 스팸/폭주 | 토큰·IP별 rate limit, 길이 제한 |
| 원본 자료 유출 | 리뷰 화면에 `raw/corpus/kb` 절대 미포함(버전 블록 텍스트만) |
| 권한 상승 | reviewer 토큰으로 편집/승인 라우트 접근 차단(라우트별 역할 검사) |
| 승인 우회 | 의료 문장 변경 시 승인 자동 해제, approver만 승인 |
| 무료 배포 휘발성 | 버전·댓글이 sqlite(휘발)면 재시작 시 소실 → **영구 저장소 필요**(기존에 논의한 유료 디스크/외부DB). 지금은 로컬 우선, 배포 영구화는 별도. |

## 9. 단계별 테스트 계획

- **단위**: 문장 분할기, claim `support_level` 산정(direct/partial/inferred/unsupported 케이스), diff 생성, 버전 증가, 토큰 만료/폐기, 역할 권한, 규칙 scope 매칭.
- **통합**: 생성→블록·claim 저장 / 편집→재검사(금지어+근거)+승인해제+diff / 리뷰링크→댓글 저장·상태전이 / 수정이벤트→규칙 승인→다음 생성 프롬프트 주입.
- **보안**: IDOR(타 병원 토큰), 만료·폐기 토큰 거부, 댓글 XSS 페이로드 escape, rate limit 동작, 리뷰 화면 원본자료 미노출.
- **마이그레이션**: 이명 편 package.json → v1 변환 후 렌더 동일성 확인, 롤백 검증.
- **회귀**: 기존 `run.py all` 파이프라인(수집→KB→대본→컴플라이언스→렌더)이 스키마 확장 후에도 통과.

## 착수 제안 순서 (스펙 1~6 준수)

1. `store/db.py` 스키마 + `store/migrate.py` (이명 편 마이그레이션 검증) — **데이터 토대**
2. 블록 ID·type 부여를 생성/마이그레이션에 반영
3. 편집 + 자동저장 + diff + 편집 시 재검사(금지어+근거)+승인해제
4. claim 단위 Source Grounding(문장 분할 + evidence 확장 + unsupported 차단)
5. 외부 reviewer 댓글 링크(토큰·역할·보안)
6. Correction Memory(edits→규칙 승인→프롬프트 주입) + 이번 Style Rule 7종 등록

> UI 전면 개편·YouTube API(P1)는 위 6 완성 후 착수.
