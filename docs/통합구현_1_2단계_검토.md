# 통합 구현 검토 자료 — 1·2단계 (A→B)

> 목적: 앞서 승인된 "최종=B, 전환=A→B" 방향으로 실제 구현한 **1단계(데이터·인증)·2단계(디자인 통일)**의 코드가 맞게 됐는지 GPT 검토.
> 배경: 대시보드(app.py, SQLite+파일, UI 좋음) + 스튜디오(web/api.py, PostgreSQL, 기능·영속 강함)를 한 Render 서비스에서 `/`·`/studio`로 운영 중. 목표는 대시보드 UI 위에 PostgreSQL 기능을 얹어 하나로 수렴.

---

## 1. 이번에 구현한 것 (요약)

**1단계 — 데이터·인증**
- `store/ingest.py`: `generation_jobs` 테이블(비파괴 additive) + `ingest_package()` (생성 결과 package.json → 대본/버전/블록/문장/주장 적재).
- `app.py` 로그인: PostgreSQL 사용자로 인증(`lookup_user_for_login`) + `session['user_id']` 설정. users.yaml은 폴백.
- `app.py` 생성 후: `_ingest_to_pg()`로 PG 적재, 병원 페이지에 "스튜디오 편집·근거·이미지·승인 →" CTA.

**2단계 — 디자인 통일**
- 스튜디오 `_CSS`를 대시보드 디자인 토큰(Pretendard·#3182F6·둥근 카드 18px·토스풍 버튼)으로 교체 → 모든 스튜디오 화면이 대시보드 룩.
- 스튜디오 `_page`에 "← 대시보드" 네비.

## 2. 기술 상세

### 2.1 생성 → PG 적재 (`store/ingest.py`)
- `generation_jobs(id, hospital_id, topic, status, idempotency_key, version_id, raw_output, error_message, retry_count, created_by_membership_id, prompt_version, ...)`, `UNIQUE(hospital_id, idempotency_key)`.
- 비파괴 additive: `CREATE TABLE IF NOT EXISTS` + RLS(app_rw 테넌트 정책 / app_owner definer 정책) + grant. **full reset 불필요.** 라이브에 이미 적용.
- `ingest_package(engine, hospital_id, topic, script_list, raw)`:
  - `idempotency_key = sha256(hospital+topic+canonical(script_list))`. 동일 재요청 → 기존 version 반환(reused).
  - **1차 트랜잭션**(`app_rw` + `tenant_conn`=RLS): job(parsing) → script(topic별) → 새 version(source='ai') → approval_state(none) → blocks(block_type_of·scene·say·metadata) → sentences(문장분할) → **claim(휴리스틱 is_claim, unverified)** → scripts.current_version 갱신 → job(completed).
  - **LLM 근거검증은 트랜잭션 밖 2차**(기존 `evidence/llm_verify` 유지) — GPT 지적 반영.
- 실패 시 예외 전파(caller가 처리). aborted tx에선 job 흔적이 롤백됨(아래 한계 참조).

### 2.2 단일 로그인 (세션 공유)
- **핵심 사실**: Render에선 대시보드·스튜디오 두 Flask 앱이 **같은 `SECRET_KEY` 환경변수**를 사용 → Flask 세션 쿠키(같은 이름 `session`, 같은 시크릿)를 **서로 읽을 수 있음**.
- 그래서 대시보드 로그인 시 `session['user_id']=PG uuid`만 세팅하면, 스튜디오가 그 값을 읽어 인증됨.
- `app.py` 로그인: (1) PG 인증(`lookup_user_for_login(email)`+`check_password_hash`) 성공 → `session['user']=email`, `session['user_id']=pg uuid`. (2) 실패 시 users.yaml 폴백.
- 무효 세션(재시드로 옛 user_id) 403 → 로그인으로 자동 리다이렉트(errorhandler).

### 2.3 디자인 통일
- `_CSS` 상수 교체(클래스명 유지 → 로직 무변경). `_page`에 로고+대시보드 링크 nav.

## 3. 검증 결과

## 4. GPT 이전 검토 반영 여부

| GPT 지적 | 반영 |
|---|---|
| A는 B로 가는 임시 단계 | ✅ 1·2단계로 진행, /studio는 임시 |
| PostgreSQL을 단일 원본 | ⏳ 신규 생성은 PG 적재. 단, SQLite도 병행 중(작업상태 job) — 완전 단일화는 3단계 |
| LLM을 DB 트랜잭션 밖 | ✅ 구조 적재(1차 tx) / claim 근거검증(2차) 분리 |
| generation_job(status·idempotency·retry) | ✅ 구현(단 실패 추적은 아래 한계) |
| 파일 R2/S3 | ❌ 미착수(3단계, 계정 필요) |
| 로그인 PG 단일화 | ⚠️ 부분: 대시보드가 PG로 인증하되 users.yaml 폴백 유지 |

## 5. 내가 아는 약점·미결 (솔직히)

1. **실패한 생성 job 추적 미흡**: ingest를 단일 트랜잭션으로 처리 → DB 오류로 aborted되면 job 행(‘failed’)도 롤백되어 흔적이 안 남음. GPT가 원한 "멈춤/실패/재시도 구분"에는 job insert를 별도 커밋으로 분리 필요.
2. **스키마 마이그레이션 이원화**: `scene_images`·`generation_jobs`는 **수동 additive 스크립트**로만 생성(Alembic 0001에 없음). Alembic과 실제 스키마가 드리프트. 정식화(마이그레이션 일원화) 필요.
3. **SQLite·PostgreSQL 병행**: 대시보드는 여전히 SQLite(job 상태)·파일 사용, 스튜디오는 PG. GPT가 경고한 이중 저장. 신규 대본은 PG에도 들어가지만 대시보드 작업상태는 아직 SQLite.
4. **users.yaml 잔존**: 로그인이 PG 우선이지만 users.yaml 폴백이 남아 인증 경로 2개.
5. **새 병원 PG 자동생성 없음**: `app_rw`는 hospitals INSERT 권한이 없어(의도적 최소권한), 대시보드에서 새 병원 만들면 PG hospital이 안 생김 → 그 병원은 스튜디오 연결 안 됨. 현재 boncure만 연결. 해결엔 admin(SECURITY DEFINER) 함수나 owner 경로 필요.
6. **병원 slug ↔ PG hospital 매핑이 이름 일치 전제**: 대시보드 `h`(폴더명)와 PG `slug`가 같다고 가정.
7. **이미지 bytea**: scene_images를 PG bytea로 저장(현재 44KB×19). GPT 권고는 오브젝트 스토리지. 커지면 DB 부하·백업·마이그레이션 부담.
8. **세션 공유의 전제**: 두 앱이 같은 SECRET_KEY여야만 단일 로그인 성립(Render는 그러함). 로컬 개발은 각각이라 안 이어질 수 있음. 또한 두 앱이 쿠키를 공유한다는 건 한쪽 취약점이 세션 전체에 영향 가능 — 최종적으론 앱/인증 단일화가 맞음.
9. **_pg_login이 로그인마다 새 엔진 생성**(경미한 비용). 커넥션 재사용 개선 여지.
10. **권한 모델 부재**: 병원 내부 역할(원장/마케터/검수자)별 행동 제한 없음. RLS는 병원 간 격리만.

## 6. GPT에게 물을 검토 질문

1. **세션 공유 방식(두 앱 동일 SECRET_KEY + session['user_id'])**을 1단계 임시책으로 수용 가능한가, 아니면 지금 단일 인증(하나의 app factory)으로 가야 하나? 보안상 함정은?
2. **ingest 실패 추적**: job insert를 content 적재와 별도 트랜잭션(먼저 commit)으로 분리해 ‘failed’를 남기는 게 맞나? 아니면 outbox/상태머신 별도 설계?
3. **idempotency_key = sha(hospital+topic+script 내용)** 설계가 적절한가? (같은 주제 재생성 시 내용이 조금만 달라도 새 버전 — 의도는 맞지만 사용자가 "재생성" 눌렀을 때 매번 새 버전이 쌓이는 것에 대한 정책?)
4. **스키마 마이그레이션 일원화**: 수동 additive → Alembic revision으로 정식화하는 순서/방법?
5. **새 병원 PG 생성**: admin SECURITY DEFINER 함수로 hospital+membership 생성 vs owner 경로 vs 대시보드에서 최소권한 부여? 권장?
6. **SQLite 제거 순서**: 대시보드 작업상태(job)를 언제/어떻게 PG로 옮길지(생성 상태를 generation_jobs로 일원화)?
7. **이미지 bytea → R2 전환** 우선순위: 지금 해야 하나, 규모 커진 뒤 해도 되나?
8. 2단계에서 CSS만 통일하고 **화면 구조(라우트)는 아직 /studio에 있음**. 대시보드 라우트(`/scripts/<id>/edit` 등)로 완전 이전을 언제 할지(사용 빈도 순)?

## 7. 현재 사용자 흐름 (참고)

로그인(대시보드, PG 계정) → 자료 업로드 → 대본 생성(run.py) → 자동 PG 적재 → 병원 페이지 "스튜디오에서 편집·근거·이미지·승인 →" → (대시보드와 동일 디자인의) 스튜디오 화면에서 이어 작업. 로그인 한 번, 디자인 하나로 보이지만 **내부적으론 저장소·인증·라우트가 아직 완전 단일화 전**(3단계 대상).
