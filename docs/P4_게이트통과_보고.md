## 2. PostgreSQL 버전별 결과

| 버전 | 방법 | 결과 |

## 4. assessment_set_hash canonical 명세 (확정)

`store/repositories.py`에 코드로, 아래 규격:
- 인코딩 **UTF-8**, **canonical JSON**(`sort_keys=True`, `separators=(",",":")` — 공백 없음)
- **claim_id 오름차순 정렬**, **effective assessment만** 포함(승인에 실제 사용된 집합)
- 포함 필드: `support_level, verification_status, medical_risk, assessment_kind`(override는 kind로 식별)
- **제외**: created_at, 랜덤 UUID, rationale 등 비결정 필드
- **domain prefix** `"boncure.v1:assessment_set:"` 접두 후 **SHA-256 hex**
- `version_content_hash`: 블록 order_index 순 `{order,type,scene,text,label,tags}` canonical → SHA-256.
- **정책**: stale = 미승인 OR (content/assessment_set/policy 해시 중 하나라도 불일치).
  - 새 assessment가 추가돼도 **effective가 안 바뀌면 not-stale**(실측). 단 새 automated가 human과 충돌하면 별도 conflict 표시·재검토는 **3/4단계 배선 예정**(현재는 stale 판정에 미포함).

## 5. RLS pool context 누수 테스트 결과

같은 pooled connection에서 H1 트랜잭션(2행) → 컨텍스트 미설정 트랜잭션(**0행**) → H2 트랜잭션(1행). `set_config(...,is_local=true)`가 트랜잭션 종료 시 리셋되어 **누수 없음** 확인.

## 6. 다중 worker lease 경쟁 결과

pending import 1건에 worker-1 `acquire_lease` 성공(lease_token 발급) → worker-2 즉시 **None**(활성 lease). 만료 강제 후 worker-2 **인계 성공**. heartbeat는 **lease_token 일치 워커만 1**, 불일치 0. (SKIP LOCKED + 만료조건 원자 UPDATE)

## 7. 동시 편집 CAS 결과

current=v1인 script에 편집자 A `create_edited_version(expected=v1)`→v2 성공(current→v2). 편집자 B(expected=v1)→**Conflict(409 대응)**. `version_no`=[1,2] **중복 없음**. (scripts FOR UPDATE + `current_version_id IS NOT DISTINCT FROM :exp` CAS)

## 8. approval / audit transaction rollback 결과

`approve_version`이 상태 UPDATE와 audit_events INSERT를 **동일 트랜잭션**에서 처리. audit 실패 주입 시 **승인 상태도 롤백**(status 'none' 유지) 실측.

## 9. 아직 미구현(4·5단계) — 명시

- **per-claim evidence 재검사(4단계)**: 마이그레이션·편집은 claim을 `unverified`(또는 automated/pending)로만 생성. 실제 source_version 원문 대조 후 assessment append는 4단계.
- **편집 엔드포인트·diff UI(3단계)**: repositories.create_edited_version 로직은 있으나 웹 라우트·diff·재분할·재검사 오케스트레이션은 3단계.
- **review_session 폐기 흐름·approval_stale UI 배선(3·5단계)**: 테이블·is_stale 함수는 있으나 런타임 라우트는 미구현.
- **notification_outbox 발송·audit 전면 배선·rate limit 정책**: 해당 기능 단계.

## 운영(관리형 PG) 주의
- **확장 불필요**: email은 `citext` 아닌 `text`+CHECK로, UUID는 PG13+ 내장 `gen_random_uuid()` → **CREATE EXTENSION 없음**.
- **역할 생성 분리**: `CREATE ROLE`(app_owner/app_rw/app_auth/platform_admin)은 관리형 PG에서 제한될 수 있어 **Alembic이 아니라 별도 DBA bootstrap**로 분리 권장. (현재 rls_sql은 DO 블록으로 idempotent 생성 — 권한 없으면 bootstrap 스크립트로 이관)
