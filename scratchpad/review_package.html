1복합 테넌트 FK

§4

generation_job_materials.material_version_id를 백필·정리 후 NOT NULL. 병원을 포함한 복합 FK로 결착해 병원 간 잘못된 snapshot 연결과 참조 중인 버전 삭제를 DB에서 차단.

(hospital_id, job_id)            → generation_jobs(hospital_id, id)  RESTRICT
(hospital_id, material_version_id) → material_versions(hospital_id, id) RESTRICT
UNIQUE(job_id, material_version_id)
cross-tenant 삽입 시도가 실제로 거부됨(테스트로 검증).

2스냅샷 봉인(sealing)

§5

job이 pending을 벗어나면 snapshot의 INSERT/UPDATE/DELETE를 트리거로 차단 — 완료된 job의 입력 자료 구성을 나중에 바꿀 수 없습니다. job에 봉인 시점·개수·매니페스트 해시를 기록.

pending → snapshot 봉인 → generating 전환(이후 sealed)
generation_jobs.material_snapshot_{at, count, hash}

3job 실행권 원자적 획득

§14

실행 시작을 compare-and-set으로: UPDATE … SET status='generating' WHERE status='pending' RETURNING. 행을 받은 워커만 LLM을 호출해 중복 실행을 차단합니다.

두 워커 동시 시도 → 하나만 True, 나머지는 실행하지 않음(테스트로 검증).

+복원 하드닝 · provisioning 경쟁

§7

복원 검증. materialize_job_snapshot은 current가 아닌 snapshot의 material_version_id 경로만 사용하고, 복원 bytes의 size·sha256을 재검증(불일치 시 생성 중단). 임시파일 기록 후 atomic rename, raw/ stale 정리.

§9

provisioning 경쟁조건. 동시 slug INSERT 충돌 시 unique_violation을 잡아 멤버면 기존 반환, 아니면 Conflict로 재판정(일반 예외를 삼켜 기존 병원 반환하지 않음).

테스트 83개 통과(신규: 봉인 후 변경 차단·원자적 획득 단독 성공·cross-tenant FK 거부). 실제 alembic upgrade head가 0001→0011 신규 DB에서 성공. 신규 스키마 전부 비파괴 additive. 라이브 DB 반영(복합 FK 5개·seal 트리거·material_version_id NULL 0 확인) + master 푸시.
